## 49. Testing Strategy

### 49.1 Shape of the suite

```text
        ▲  E2E (10–15 flows, real stack)          slow, few
       ╱ ╲ Integration/API (per endpoint + DB)    medium, many
      ╱   ╲ Unit (domain logic, pure)             fast, most
     ╱_____╲ Static (types, lint, schema)         instant, always
```

**Non-negotiables enforced in CI:**
- `packages/shared` order state machine: **100% branch coverage**.
- Domain services (order, cart, inventory, prep-time, auth, permissions): **≥ 85%**.
- Overall API: **≥ 70%**, no PR may lower coverage.
- Any bug fix ships with a regression test that fails before the fix.

### 49.2 Layers

| Layer | Scope | Tools | Notes |
|---|---|---|---|
| Static | types, lint, dead code, import boundaries | tsc strict, ESLint (+ custom `no-cross-module-import` rule), Prettier | The boundary lint rule is what keeps the monolith modular |
| Unit | state machine, pricing/tax/discount math, permission resolution, availability derivation, ETA math, validators | Jest | No DB, no mocks of our own code where a real object will do |
| Integration | repository + service + real PostgreSQL/Redis via Testcontainers; transaction rollback per test | Jest + Testcontainers | Includes migration up/down on every run |
| API/contract | every endpoint: authz matrix, validation, error codes, pagination, idempotency | Supertest + generated OpenAPI validation | Table-driven authz tests: for each endpoint × role → expected status |
| Database | constraint and index assertions (partial unique on active cart, unique idempotency, append-only audit), migration reversibility, `EXPLAIN` guards on the §39 queries | Jest + SQL fixtures | Catches "the index that quietly disappeared" |
| Real-time | socket auth, room authorisation, event fan-out across two API instances, reconnect reconciliation | Jest + socket.io-client + two app instances on one Redis | Multi-instance test is mandatory — single-instance tests hide adapter bugs |
| Concurrency | last-item race (N parallel orders → exactly one success), duplicate submit with same idempotency key, concurrent status transitions | Jest with parallel promises against real DB | The highest-value tests in the suite |
| UI component | design-system + screen components | Jest + React Native Testing Library / RTL | |
| E2E mobile | the golden flow on Android emulator | Detox / Maestro | Runs nightly, not per-PR |
| E2E web | admin verification + order monitoring flows | Playwright | Per-PR on a smoke subset |
| Security | authz fuzzing (role × endpoint), IDOR probes on every `/:id`, OTP brute force, upload of EICAR + polyglot + oversized files, dependency and secret scanning, ZAP baseline | Jest + gitleaks + `npm audit` + OWASP ZAP | Malicious-file tests are part of the definition of done for §22 |
| Performance | nearby search at 100k branches, catalog page, order placement, message send | k6 | Seeded synthetic dataset generator in `infra/seed` |
| Load/soak | peak-hour profile (order burst + chat + sockets), 1 h soak for leaks | k6 + socket load script | Gate before each city launch |
| Failure/recovery | DB failover, Redis restart (sockets must recover), provider outage (SMS/push/storage), worker crash mid-job, outbox backlog drain, network partition on mobile | Toxiproxy + chaos scripts in staging | Every one has a runbook assertion |

### 49.3 Critical E2E flow (must pass before any release)

```text
customer registers (OTP) → sets location → nearby list shows seeded shop
→ opens shop → adds 3 products → preflight clean → places order (idempotency)
→ shop app receives socket event + push → acknowledges → accepts with 15 min
→ customer sees ETA + system message → chat exchange with an image upload
→ shop marks preparing → packing → one item UNAVAILABLE → customer approves
   removal → totals recomputed → packed → ready
→ customer receives CRITICAL notification with pickup code
→ customer marks arrived → shop verifies code → handed over → completed
→ payment recorded as PAY_AT_STORE/CAPTURED → review submitted (V2)
→ assertions: order_status_history complete and ordered, inventory ledger balanced,
  notification_delivery has no duplicates, audit_log entries present
```

Additional mandatory E2E variants: reject path, expiry path (no shop response),
customer cancel path, no-show path, document/quote path (print shop),
duplicate-submit path, offline-shop path (socket down, push only).

### 49.4 Test data & environments
- Deterministic seed script: cities, categories, master products, 3 businesses ×
  2 branches, 200 products, customers, and one order in every state (invaluable for UI
  work and for admin screens).
- No production data in lower environments; anonymised dumps only, generated by a
  documented scrubber.
- Every test creates its own tenant; no shared mutable fixtures.

## 50. DevOps Strategy

### 50.1 Environments

| Env | Purpose | Data | Deploy |
|---|---|---|---|
| local | dev | `docker-compose` (Postgres+PostGIS, Redis, MinIO, MailHog, ClamAV) + seed | manual |
| ci | tests | ephemeral Testcontainers | per push |
| staging | pre-prod verification, load, chaos | anonymised/seeded | auto on merge to `main` |
| production | live | real | manual promotion of the staging-verified image |

### 50.2 Branching & review
- Trunk-based: short-lived `feature/*` branches → PR → squash merge to `main`.
- PR requires: green CI, ≥1 review, coverage not lowered, migration reviewed
  separately, ADR link for architectural change.
- Conventional commits → automated changelog and semantic version tags.
- `main` is always deployable; feature flags hide incomplete work (no long-lived
  feature branches).

### 50.3 Pipeline (< 15 min)

```text
push → install (pnpm, cached) → typecheck → lint + boundary rules → unit
     → integration (Testcontainers) → API/contract → build docker image
     → security scan (audit, gitleaks, image CVE) → push image
merge to main → migrate staging → deploy staging → smoke E2E + k6 smoke
             → manual approval → migrate prod (expand) → rolling deploy
             → post-deploy smoke → (contract migration in a later release)
```

### 50.4 Deployment & migrations
- Immutable container images tagged by commit SHA; identical artifact across envs.
- Rolling deploy with health-gated instance replacement; zero downtime.
- **Expand → migrate → contract** for schema changes so old and new code coexist:
  add nullable column → backfill in a job → switch reads → drop later. No blocking
  `ALTER`s on large tables; `CREATE INDEX CONCURRENTLY`.
- Rollback: previous image redeploy (always safe because migrations are
  backwards-compatible within a release window); data-affecting rollbacks use forward
  fix scripts, never `DROP`.
- Config strictly via env vars, validated at boot with zod — the process refuses to
  start on missing/invalid config rather than failing at 3 a.m.
- Secrets in a managed store, injected at runtime, rotated on a schedule; `.env.example`
  is the only env file in git.

### 50.5 Backups, DR, runbooks
- Managed Postgres: automated daily snapshots + PITR (WAL) → RPO ≤ 5 min,
  RTO ≤ 1 h; **restore drill quarterly** (a backup that has never been restored is not
  a backup).
- Object storage versioning + lifecycle rules; Redis is treated as disposable (nothing
  durable lives only in Redis).
- Runbooks in `docs/runbooks/`: DB failover, Redis loss, provider outage (SMS/push),
  outbox backlog, stuck orders, mass notification failure, secret rotation, incident
  comms, city launch checklist.

### 50.6 Observability
- **Logs:** pino JSON, one line per request + domain event, with `requestId`, `userId`,
  `businessId`, `orderId`. PII redaction allow-list. Shipped to Loki/hosted.
- **Metrics (RED + domain):** request rate/errors/duration per route; queue depth and
  job latency; socket connections; outbox lag; and the domain KPIs that actually matter
  — `orders_placed`, `order_accept_latency_seconds`, `orders_expired_total`,
  `eta_absolute_error_minutes`, `notification_delivery_failures_total`,
  `inventory_conflict_total`.
- **Traces:** OpenTelemetry across HTTP → service → DB → queue → worker, so
  "order placement is slow" is answerable in one trace.
- **Errors:** Sentry with release tagging and source maps (API + mobile).
- **Alerts (paging):** p99 latency, 5xx rate, outbox lag > 60 s, push failure rate,
  unacknowledged orders > threshold, DB connection saturation, disk/replica lag.
  Each alert links to a runbook. **No alert without an action.**
- **SLOs:** order placement success ≥ 99.9%; notification within 30 s ≥ 99%;
  API availability ≥ 99.5% (V1). Error budgets gate feature work.

## 51. Major Risks

| # | Risk | Impact | Likelihood | Mitigation |
|---|---|---|---|---|
| R1 | **Shops don't respond to orders** (the platform's death condition) | Fatal | High | Loud escalating alerts + SMS fallback; auto-expiry with apology + alternatives; per-branch acceptance-rate score that demotes unreliable shops in discovery; onboarding requires an alert test |
| R2 | **Catalog onboarding effort** kills supply activation | Fatal | High | Master catalog + barcode scan + CSV import + assisted onboarding; availability-only inventory mode; "top 50 SKUs" launch target rather than full catalog |
| R3 | Stale availability → customer arrives to a missing item | High | High | Daily "review availability" nudge, packing-time substitution flow, availability confidence signals, shop reliability score |
| R4 | Two-sided cold start (no shops → no customers) | Fatal | High | Neighbourhood-by-neighbourhood launch; sign 20–30 shops in one area before any demand marketing; measure density per pincode |
| R5 | Customers keep using WhatsApp/phone instead | High | Medium | Ship the differentiators that WhatsApp cannot: catalog+availability, ETA, notifications, repeat order, history; shops get a real order queue |
| R6 | ETA inaccuracy erodes the core promise | High | Medium | Append-only delay model, honest "+10 min" updates, measure `eta_absolute_error`, heuristic suggestions before ML |
| R7 | Malicious file uploaded to a shop device | High | Medium | Mandatory AV scan before availability, MIME/magic validation, signed short-lived URLs (§22) |
| R8 | Account takeover via OTP/SIM swap | High | Medium | Throttles, lockouts, device binding, new-device notification, MFA for shop owners (V2) |
| R9 | Inventory race sells the last item twice | Medium | Medium | Row locks + reservations + explicit unavailable path (§40) |
| R10 | Notification provider outage during peak | High | Medium | Multi-channel fallback (push → in-app → SMS), retries with backoff, provider abstraction with a second provider configured |
| R11 | Chat table growth dominates the DB | Medium | High (over time) | Partitioning plan, retention policy, extraction path (§27) |
| R12 | Geocoding/maps provider cost spike | Medium | Medium | Aggressive caching, provider port with an OSM fallback, autocomplete debouncing, per-user quotas |
| R13 | Pharmacy/prescription regulatory exposure | High | Medium | Category gated behind legal review; prescription upload treated as sensitive data class |
| R14 | Privacy/data-protection non-compliance | High | Medium | Data minimisation, retention, export/delete, audited PII access, external legal review before launch |
| R15 | Premature scaling complexity burns the runway | Medium | Medium | Trigger-based evolution ladder (§25.2); ADR required to add infrastructure |
| R16 | Monolith degrades into a mud ball | Medium | Medium | Import-boundary lint rule, module public interfaces, event-only cross-module reactions, architecture review per module |
| R17 | Shop app used on old low-end Android with poor connectivity | High | High | Offline-tolerant queued writes, idempotent APIs, small payloads, aggressive caching, min-spec device in the test matrix |
| R18 | Key-person/single-maintainer risk | Medium | Medium | Documented decisions (this doc), ADRs, runbooks, no undocumented manual infra |
| R19 | Fraud/abuse (fake orders, review manipulation) | Medium | Medium | Order limits, no-show tracking, review eligibility rules, moderation queue, anomaly detection (V4) |
| R20 | Shop routes customers off-platform to dodge fees | Medium | Medium (post-monetisation) | Subscription rather than per-order commission; value tied to the tool, not the transaction |

## 52. Edge Cases and Resolutions

| # | Edge case | Resolution |
|---|---|---|
| 1 | Product unavailable after being added to cart | Cart mutation + `preflight` revalidate; inline notice with alternatives; blocked from checkout until resolved |
| 2 | Product unavailable after order placement | Packing checklist marks `UNAVAILABLE` → customer approves removal/substitution → totals recomputed and versioned |
| 3 | Shop rejects order | `REJECTED` with reason code; customer notified with nearby alternatives; conversation becomes `SYSTEM_ONLY` |
| 4 | Shop closes after order placement | Branch `accepting_orders=false` does not affect live orders; unaccepted orders auto-`EXPIRED`; accepted ones must be honoured or explicitly rejected with reason |
| 5 | Customer cancels | Allowed ≤ `PACKING`; reservations released; shop notified; frequent cancellers rate-limited |
| 6 | Shop delays order | Append `+N min` adjustment → new ETA → notification; repeated delays hit the reliability score |
| 7 | Customer never arrives | Reminder at ready+2 h, ready+6 h; `EXPIRED` at branch `pickup_expiry_hours`; shop decides restock; no-show counted |
| 8 | Customer arrives before ready | `CUSTOMER_ARRIVED` allowed from `READY_FOR_PICKUP` only; earlier arrival shows current ETA and pins the order at the top of the shop queue |
| 9 | Duplicate order submission | `Idempotency-Key` + unique `(cart_id)`; same order returned, button disabled client-side |
| 10 | Duplicate payment (V2) | Payment idempotency key + provider event dedupe + reconciliation job auto-refunds duplicates |
| 11 | Network disconnect mid-action | Client queues the mutation with a stable idempotency key and retries with backoff; UI shows pending state, never a false success |
| 12 | Chat message fails to send | Local `SENDING` state, retry with the same `client_message_id`, manual retry affordance, no duplicates server-side |
| 13 | File upload fails | Resumable/retryable pre-signed PUT; `media_object` stays `PENDING` and is GC'd; user sees a retry action |
| 14 | Oversized file | Rejected at intent time (before bytes move) with the limit stated |
| 15 | Malicious file | Quarantined by scan; sender warned; repeated attempts flag the account; never served |
| 16 | Shop loses internet | Push wakes the app; unacknowledged critical orders escalate to SMS; on reconnect the app reconciles via REST |
| 17 | Customer loses internet | Order state is server-authoritative; notifications retry; on reopen the app refetches |
| 18 | Business changes price mid-cart | Snapshot + explicit diff acceptance; accepted orders keep their snapshot |
| 19 | Business changes hours | Discovery reflects immediately; live orders unaffected; scheduled orders (V3) revalidated |
| 20 | Branch becomes inactive with live orders | Blocked from going inactive until live orders are terminal, or admin force-cancels with notification |
| 21 | Inventory conflict / negative stock | Conditional decrement never allows negative; a correction transaction records reality; alert on ledger mismatch |
| 22 | Two customers order the last item simultaneously | Row lock: one succeeds, the other gets `ITEMS_UNAVAILABLE` with the available quantity before placing |
| 23 | Payment succeeds but order creation fails (V2) | Order draft precedes payment; orphan captures reconciled and auto-refunded; alert raised |
| 24 | Order succeeds but notification fails | In-app notification written in the same commit; external channels retried; failure metric alerts; shop queue is the fallback surface |
| 25 | Duplicate notification | `dedupe_key` unique + `processed_event` consumer dedupe + client dedupe by `eventId` |
| 26 | Clock skew between client and server | All timestamps server-generated; clients render relative to server `now` from response headers |
| 27 | Staff member removed mid-order | Permissions re-resolved per request; the order stays with the branch, not the individual |
| 28 | Customer deletes account with a live order | Deletion request queued; executed only after all orders are terminal |
| 29 | Same phone used for customer and shop staff | Single `user` with multiple scoped roles (§16.4) |
| 30 | Pickup code shared/leaked | Single-order scope, invalidated after hand-over, mismatch attempts throttled and logged; QR/OTP in V2 |

## 53. Recommended Development Sequence

Phases map to the master plan; each phase ends with tests, a demo, and a short review
that may change the next phase.

| Phase | Deliverable | Definition of done |
|---|---|---|
| 0 | Product discovery & architecture (**this document**) | Reviewed and approved |
| 1 | Monorepo skeleton, CI, docker-compose, config validation, health checks, logging/tracing, `packages/shared` bootstrap | `pnpm dev` runs API + one client; CI green |
| 2 | Domain model in Prisma: identity, business, branch, catalog, inventory core; migrations + seed | Migrations reversible; seed produces a browsable dataset |
| 3 | Auth & RBAC: OTP, password, tokens + rotation, sessions/devices, permission guards, rate limits | Authz matrix tests pass for every role |
| 4 | Business & branch management + admin verification/approval | A shop can register and be approved end-to-end |
| 5 | Catalog + master catalog + CSV import | 50 products onboarded in < 10 minutes in a usability test |
| 6 | Inventory (3 modes) + ledger + bulk availability sweep | Ledger balances; conflict tests pass |
| 7 | Location engine + discovery + search | Nearby p95 < 400 ms on 100k seeded branches |
| 8 | Cart + preflight | All §52 cart edge cases covered by tests |
| 9 | **Order state machine + placement + transitions + outbox** | 100% state-machine coverage; concurrency tests pass |
| 10 | Real-time gateway (orders + presence) | Two-instance fan-out test passes |
| 11 | Conversations & messages (+ system messages from order events) | Reconnect reconciliation test passes |
| 12 | Media pipeline (pre-signed upload, scan, thumbnails, page count) | EICAR/polyglot/oversize tests pass |
| 13 | Prep-time & delay engine | ETA error metric emitted |
| 14 | Notifications (in-app, push, SMS/email transactional) + preferences + escalation | No duplicates under retry; escalation verified |
| 15 | Pickup code + hand-over + completion | Golden E2E flow green |
| 16 | Customer mobile app (full V1 flow) | Golden flow on device |
| 17 | Shop mobile app (queue, packing, alerts, offline tolerance) | Usability test with a real shopkeeper |
| 18 | Admin web (dashboard, verification, users, orders, config, audit) | Ops can run a launch without engineer help |
| 19 | Observability, alerts, runbooks, backup/restore drill | Restore drill completed |
| 20 | Security hardening + pen-test fixes + privacy review | ASVS L2 checklist; legal sign-off |
| 21 | Performance & load testing, index tuning | k6 targets met |
| 22 | Pilot launch: one neighbourhood, 20–30 shops, instrumented | MVP success metrics (§13) measured |
| 23+ | V2 per §14, gated on pilot metrics | |

**Parallelisation note:** phases 16–18 (clients) start as soon as the relevant API
contracts exist (phases 9–11 define them), using the generated typed client against a
seeded dev environment. Backend phases 2–15 are mostly sequential because each is a
dependency of the next.

## 54. Open questions requiring the founder's decision

1. **Launch geography and language** — which city/neighbourhoods, and which regional
   language beyond English?
2. **Launch categories** — confirm grocery + print/xerox first; pharmacy needs legal
   review before inclusion.
3. **Provider choices with cost/geo implications** — SMS provider, maps/geocoding
   provider, cloud (AWS vs. GCP vs. Fly/Render), and the monthly infra budget ceiling.
4. **Brand name** — this document uses "QuickPick" as a placeholder; a trademark check
   is required before app-store submission.
5. **Order acceptance SLA and expiry defaults** — proposed 10 min accept timeout,
   24 h pickup expiry.
6. **Free-tier caps** for the eventual freemium plan (orders/month, branches, staff).
7. **Support model** — who answers a shop's phone call at 8 pm during the pilot?
8. **Legal review owner** for privacy policy, terms, and pharmacy compliance.
